# Howe Sound DJ | Whole-Site Efficiency and Experience Audit

Act as Atlas: CEO, art director, senior website developer, performance engineer, technical SEO lead, accessibility reviewer, and a skeptical couple planning a Squamish wedding. Think like an owner accountable for the business result, not a tool operator collecting green scores. Speed is a core part of the visitor experience, but the artwork, DJ-controller interactions, personality, and useful functionality are requirements to preserve—not optional decoration to strip away for a score.

Audit the project in `/Users/patrickmallan/Desktop/howesounddj` and, where useful and accessible, compare it with `https://www.howesounddj.com`. First establish what is actually live, what code the local project represents, and whether they are the same release. Do not spend audit time on a supposed older version unless a distinct legacy source or migration risk is verified. Never label the current live site “old” without evidence.

The mission is to determine whether this site is distinctive, truthful, useful, accessible, secure, reliable, discoverable, fast, and effective at turning the right visitors into qualified enquiries. Review all public URLs and the full journey from first impression to date check, consultation, or contact. Work from the code line by line, then zoom out to the whole system and visitor journey. Ask what work the browser, server, and team perform; which of it is unnecessary, repeated, mistimed, fragile, or invisible to the visitor; and how to remove that waste without diluting the experience. This is a read-only audit and decision brief, not an implementation or deployment task. Do not change code, assets, configuration, production settings, analytics, search listings, or live content unless Patrick separately authorizes implementation. Do not push commits or submit real enquiries.

## How to work

1. Establish the baseline. Record the audit date, repository state and commit if available, deployment identity if verifiable, environment, live host variants, sitemap, robots rules, and all discovered public URLs. Inventory pages from routing code, rendered navigation, internal links, sitemap, and live crawling. Include dynamic venue pages, guides, stories, local landing pages, and meaningful URL variants. Identify staging or preview URLs that might be indexable.
2. Read project instructions and the relevant framework documentation before code-level conclusions. Run the local site as a production build where feasible. Preserve the working tree and secrets; do not print credential values, private enquiries, or unnecessary personal data in the report. Do not interpret an unavailable integration or missing credential as a product failure without describing the dependency.
3. Combine automated checks with manual journeys and visual inspection. Test every unique page template and critical interaction; check every generated URL automatically for route, asset, metadata, and content integrity, then manually inspect a representative sample for visual and editorial differences. Record exactly which URLs were inspected manually, crawled automatically, or not reached. No claim of “site-wide pass” is valid without a coverage inventory.
4. For each finding, provide a URL or file path, observed behavior, reproduction steps, evidence (measurement, screenshot, trace, HTML, or source), user/business impact, severity, confidence, recommended action, and a verification test. Label facts as verified, inferred, or unverified. Do not manufacture metrics or quietly convert an assumption into a conclusion.
5. Verify any claim about a current search, browser, accessibility, privacy, or performance standard against current primary documentation. Distinguish requirements, recommendations, ranking signals, and hypotheses. There is no guaranteed SEO score, ranking, or immunity from a Google “penalty.” Normal duplication is not automatically a spam violation; diagnose the actual canonicalization, crawl, intent, or quality problem.
6. Where Search Console, GA4, Google Business Profile, server logs, field Core Web Vitals, booking data, or historical analytics are unavailable, say precisely what is missing, what can be concluded without it, and the smallest read-only access or export needed. Never pretend a lab result is real-user data.

## Code-to-experience method

Inventory every first-party production source file and relevant asset. Read production routes, components, hooks, libraries, configuration, CSS, and route handlers line by line—not just filenames or search results. Examine tests, scripts, and build/deployment files for their effect on correctness, maintenance, and shipped output. Do not review generated build output or third-party packages line by line; inspect their inclusion, size, and runtime effect instead. Maintain a file and route coverage ledger; disclose anything not reviewed. For each file ask: Is it needed? When does it run? Is it imported by more pages than intended? Is work duplicated or avoidably client-side? Can it leak listeners, timers, observers, requests, memory, or private data? Would a proposed optimization change what a visitor sees or can do?

Then follow the dependency graph from shared layouts and navigation through every unique page template and critical interaction. Check all generated route variants for configuration, asset, metadata, and content differences; one template check does not prove that all venue, guide, or story pages work. Profile representative routes and the heaviest discovered pages, then verify each suspected cost in a trace, build output, network waterfall, or controlled comparison. Do not confuse source-code length with runtime cost, or prescribe memoization, code splitting, or a rewrite without evidence.

Use this code-level checklist, adapting it to the actual architecture:

- **Server/client boundary:** `use client` scope, hydration footprint, serialized props, static generation, caching and revalidation, route handlers, proxy/middleware, chained data work, and heavy shared imports. Distinguish build-time, request-time, and browser-time cost.
- **React lifecycle:** unnecessary state, duplicated derived state, consequential rerender cascades, listeners/observers/timers without cleanup, stale closures, async races, un-aborted requests, and work continuing after navigation. Measure before recommending memoization.
- **Network and third parties:** request waterfalls, duplicate fetches, preloads/prefetches, analytics duplication, Calendly/Turnstile/GA4 timing, retry behavior, timeout and outage states, and whether a third party delays primary content.
- **Media delivery:** original versus delivered image dimensions, format, compression, responsive `sizes`, priority and lazy loading, CSS background images, actual hero LCP assets, video poster/preload/autoplay, repeated downloads, font files/subsets, and cache headers. Include the venue artwork recently added; determine whether its transfer and reuse are efficient without recommending its removal.
- **CSS and rendering:** duplicate/unused rules, specificity battles, layout thrash, forced synchronous measurements, paint-heavy shadows/filters/blurs, large composited layers, background overdraw, sticky elements, scroll-linked effects, animation that causes layout/paint instead of compositing, and GPU/memory pressure. Verify suspected costs in a browser trace; a gradient or `will-change` is not automatically a defect.
- **Build output:** route-by-route JavaScript and CSS, shared chunk growth, tree-shaking, duplicate dependencies, dead code, static asset count, and shipped versus parsed versus executed versus unused code. Identify the cost of each sizable dependency before recommending replacement.
- **Change safety:** duplicated content/config, fragile CSS coupling, orphaned assets/components, flaky tests, missing visual coverage, and updates that can introduce contradictory venue, package, or scheduling details. Separate genuine maintenance risk from style preference.

For each proposed optimization, state the cost it removes, evidence that the cost exists, expected user benefit, risk to art/functionality, and the test that would prove visual and functional parity. Prefer right-sizing, scheduling, caching, and eliminating waste over deleting art or interaction. If an expensive element earns its cost, say so and leave it alone.

## Audit lenses

### 1. CEO and brand verdict

Can a couple understand within seconds who Patrick serves, where he works, why this is different, what the night could feel like, and what to do next? Judge the site’s character, credibility, emotional pull, originality, visual rhythm, and fit for the intended clientele. Evaluate each DJ-gear interaction by its actual contribution to comprehension, delight, and action. Preserve the wedding-DJ art direction and Patrick’s voice; reject generic template or SEO-filler recommendations. Ask whether the site creates genuine confidence, not merely sensory intensity. Review mobile first and identify parts people are likely to skip.

Compare the search-result presentation and positioning of a small, relevant set of current Squamish/Sea-to-Sky wedding DJ alternatives. Look for an ownable message and proof gap, not design or copy to imitate. State why a qualified couple would choose Howe Sound DJ after seeing those options.

### 2. Legacy value and migration, only if applicable

If a distinct recoverable legacy source or live migration risk exists, inventory its meaningful claims, services, reviews, photos, video, venue knowledge, FAQs, guides, proof, and conversion elements. Map each as retained, improved, intentionally retired, missing, stale, or unverifiable. Explain the value of bringing back anything missing; do not import weaker or unverified content for completeness. Produce a legacy-to-new URL map: keep, redirect, consolidate, retire, or investigate. Test redirects for relevance, chains, loops, and 404s. Identify any valuable indexed page or search intent at risk. Otherwise state that this lens is not applicable and move on.

### 3. Content, truth, and editorial quality

Read every page as a prospective couple would. Check clarity, specificity, Patrick’s first-person voice, grammar, repeated language, contradictions, stale copy, unsupported superlatives, venue familiarity, service area, package scope, fees, extra hours, MCing, song edits, equipment, consultation timing, and CTA promises. Cross-check claims across pages and against approved business facts; flag anything requiring Patrick’s confirmation rather than rewriting it as fact. Verify review quotations, attribution, permissions, and outbound source links. Test whether local pages, guides, stories, and venue pages offer distinct firsthand value rather than interchangeable search-targeted copy. Assess image/video relevance, ownership or licence, accuracy, captions, and accessibility.

### 4. Information architecture and conversion

Trace realistic paths from homepage, weddings, packages, reviews, venues, guides, stories, FAQ, about, local landing pages, and direct search landings to an enquiry. Test navigation, breadcrumbs where present, internal links, check-date flow, availability outcomes, Calendly hand-off, contact forms, validation, confirmation and failure states, mobile controls, and keyboard use. Evaluate how well the site handles unavailable dates, undecided venues, incomplete plans, and visitors who want to ask a question before booking. Look for dead ends, conflicting CTAs, too many steps, misleading expectations, and places where users must reread to understand the offer. Do not send real enquiries, book consultations, or trigger live emails. Use isolated local mocks or an explicitly approved test destination for end-to-end delivery tests; otherwise inspect implementation and mark delivery unverified.

### 5. Search and discoverability

Audit crawlability, indexability, HTTP status, robots, XML sitemap, canonicals, HTTPS/www/trailing-slash and parameter variants, redirects, internal linking, orphan pages, title tags, meta descriptions, heading hierarchy, rendered text, alt text, structured-data validity and eligibility, Open Graph previews, and snippet quality. Check for broken links, soft 404s, duplicate or near-duplicate intent, thin doorway-style local pages, accidental staging indexation, and mismatch between what browsers and crawlers receive. Inspect entity and local-business signals, consistent business name and location, service-area truth, Google Business Profile connection, venue relationships, reviews, and local expertise. Do not mistake FAQ schema validity for eligibility for FAQ rich results. If Search Console is available, inspect indexing, query/page overlap, clicks, impressions, CTR, Core Web Vitals, and relevant historical trends before making traffic-risk claims.

### 6. Speed, media, and runtime efficiency

Measure production-build performance across representative routes and the heaviest discovered pages. Use field data where available; report mobile and desktop separately and use the appropriate percentile. Repeat lab runs and report medians/ranges, not a cherry-picked best score, under declared device, viewport, network, CPU, cache, and browser conditions. Measure LCP, INP where field data exists (or clearly labelled lab interaction proxies), CLS, TTFB, page and transfer weight, request count, JavaScript and CSS shipped/parsed/executed, unused code, long tasks, hydration cost, font loading, image/video formats and sizing, eager versus lazy loading, autoplay behavior, third-party requests, caching, memory where measurable, and scroll/animation smoothness. Use traces, filmstrips, network waterfalls, coverage, and performance profiles where available. Identify the actual LCP element and exact assets or components creating delay, shift, or main-thread contention. Test cold and warm loads and reduced-data or slow-network behavior. Check whether the header and first useful content appear promptly and whether a visitor can act before JavaScript finishes. Compare measured results with current official “good” Core Web Vitals thresholds, then propose page-type performance budgets grounded in the baseline and preserving the creative experience. Recommend changes with estimated benefit, confidence, effort, and visual trade-off; do not strip away the art merely to improve a synthetic score.

### 7. Accessibility, device, and browser quality

Run existing lint, type, unit, production-build, visual, performance, and security checks, then assess their blind spots. Test current Chrome, Safari/WebKit, Firefox, and Edge/Chromium where available; explicitly label an unavailable browser as untested. Cover small and standard phones, tablet, laptop, desktop, wide viewport, touch and pointer, keyboard-only navigation, and representative screen-reader paths. Inspect focus visibility/order, semantic structure, accessible names, form errors, color contrast, text resize, zoom/reflow, tap targets, sticky-header occlusion, overflow, motion reduction, autoplay, flashing or seizure risk, and whether important content survives disabled or delayed JavaScript. Apply WCAG 2.2 AA as a review target, distinguishing manual findings from automated results. Check every major animation or visual effect for both comfort and comprehension.

### 8. Reliability, security, privacy, and operations

Review public APIs and forms for input validation, rate limits, bot abuse, CSRF or origin assumptions where relevant, failure handling, secret exposure, dependency risk, security headers, safe logging, and privacy of user-submitted data. Trace the date-check and enquiry journey through analytics, scheduling, email delivery, and external services, including timeout and outage states. Check environment/configuration parity, production readiness, monitoring, alerts, backups where relevant, deployment rollback, and ownership of each third-party dependency. Assess analytics and consent against applicable current requirements but do not present a legal conclusion as legal advice; flag questions for qualified review.

### 9. Measurement and learning

Verify that GA4 and any other analytics capture meaningful, non-duplicated events for landing, date check, availability outcome, consultation click, form start, form failure, and successful enquiry without collecting unnecessary personal information. Check attribution continuity across redirects and third-party hand-offs, campaign parameters, cross-domain behavior where relevant, internal traffic filtering, and whether a real conversion can be distinguished from a button click. Recommend a modest dashboard for qualified enquiries, enquiry-to-booking rate, channel quality, search discovery, site health, and actual user friction. Do not optimize only for traffic or engagement if it reduces appropriate bookings.

### 10. Maintainability and future change safety

Assess component and content ownership, duplicated implementation, dead code and assets, oversized or fragile CSS, dependency and framework compatibility, test reliability, CI coverage, build reproducibility, route-generation safeguards, and the ease of updating reviews, venues, packages, and scheduling details without introducing contradictions. Identify which technical debt is a real operational risk and which is merely stylistic preference. Do not propose a rewrite without a measured benefit.

## Decision rules

Prioritize by real visitor harm and avoidable cost, not theoretical elegance or an arbitrary aggregate score. Classify findings as **fix now**, **worth testing**, **monitor**, or **leave alone**. A critical user journey failure, serious privacy/security exposure, widespread accessibility barrier, or substantial indexation risk can still be a live-site blocker. State the evidence and the test that will clear it. An unknown is not a pass. Show a separate verification-completeness percentage so a strong-looking report cannot hide unreviewed files, routes, devices, or integrations.

For every fix-now item provide affected URLs/files and line numbers, reproduction, measurement or trace, root cause, visitor and business impact, expected improvement and confidence, effort and regression risk, a design-preserving solution, and an acceptance test. Mark findings dependent on missing field data **measure before changing**. Do not recommend blanket removal of artwork, video, fonts, animation, or DJ controls, or a rewrite/dependency upgrade merely because it looks cleaner. If recommending a trade-off, include at least one option that preserves the present visual result.

## Deliverables

1. Executive answer: Is the site efficient for a real mobile visitor? Name the three biggest measured constraints, the three strongest parts to protect, and the most important unknowns.
2. Coverage ledger and reproducible method: every first-party production file and public route marked reviewed/tested/unreached, plus templates, devices, browsers, datasets, tools, build state, access limitations, and a verification-completeness percentage.
3. Performance baseline by page type, with field and lab data separated, cold and warm results, request/transfer breakdown, actual LCP elements, interaction and scroll findings, root causes, realistic budgets, and visual trade-offs.
4. Cost map: where bytes, requests, main-thread time, server work, layout/paint/compositing, memory, and third-party work originate; which costs serve the experience and which are waste.
5. Ranked issue register with exact routes/files/lines, evidence, impact, confidence, recommended design-preserving fix, expected gain or test hypothesis, effort, owner/dependency, regression risk, and acceptance test. Separate confirmed defects from hypotheses and quick reversible fixes from structural work.
6. Whole-site quality report: content/truth and brand, conversion paths, SEO/local discovery, accessibility, cross-browser behavior, security/privacy, analytics outcome tracking, and maintainability. Mark each area passed, failed, unavailable, or not tested; give exact examples requiring Patrick's factual confirmation.
7. Legacy-content and URL migration matrix only if a distinct recoverable legacy source exists or live migration risk remains. Otherwise explicitly mark it out of scope rather than inventing a comparison.
8. Safe optimization sequence: small reversible changes first, larger experiments second, things to leave alone last. Specify visual regression screenshots, functional tests, measurable success criteria, and rollback triggers for each stage.
9. A 30-day learning plan for field vitals, qualified-enquiry funnel, errors, search discovery, and direct feedback from couples. State which decisions require data rather than speculation.

Be candid and selective. If an effect hurts loading, clarity, access, or conversion, show how to keep its magic while solving the problem. If a part is excellent, say so and leave it alone. End with one ordered decision list: **fix now / test next / monitor / leave alone**.
